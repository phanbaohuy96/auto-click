# `minSdk 30` — Android 11, the last cheap floor

The Android app targets `minSdk 30` / `targetSdk 36`, overriding the `minSdk 24` inherited from the
`android-base-structure` template. This is the same shape of decision as
[ADR-0001](../../../docs/adr/0001-screencapturekit-and-min-macos-14.md) on macOS: an operating-system
floor bought deliberately, in exchange for a smaller surface to be correct on.

## The floor was chosen by where the cliff is

Cumulative device distribution, April 2026 (<https://apilevels.com>):

| `minSdk` | Android | Reach | Cost of the step |
|---|---|---|---|
| 26 | 8.0 (2017) | 96.1% | — |
| 28 | 9 (2018) | 93.5% | 2.6 pts |
| 29 | 10 (2019) | 91.1% | 2.4 pts |
| **30** | **11 (2020)** | **86.9%** | **4.2 pts** |
| 31 | 12 (2021) | 78.8% | **8.1 pts** |
| 33 | 13 (2022) | 68.9% | 9.9 pts |
| 34 | 14 (2023) | 54.5% | 14.4 pts |

API 30 is the **last step before the first real cliff**. Everything up to it costs a few points;
the step past it costs twice as much as any step before it. What is given up is Android 10 and
older — phones from 2019 and earlier.

## The reason is the test matrix, not the reach

Reach is the weaker argument here: the app is sideloaded rather than published (Google Play does
not permit this use of the Accessibility API), so there is no store ranking and no growth curve to
defend.

The argument that decides it is that each API level below the current one is a **different set of
rules to be correct under**, and this project's standard is that what is not tested on real
hardware is not supported. `README.md` already says so about macOS: *"`swift test` proves the
logic; it does **not** prove the app clicks the right place on a real screen."* The same honesty
applied here counts behavioural regimes, not percentages:

- at `minSdk 30`: **four** — `30`, `31–32` (overlay touch rules), `33` (runtime notification
  permission, restricted settings for sideloaded apps), `34+` (foreground service types).
- at `minSdk 24`: **eight**.

An emulator weakens this argument and the weakening should be admitted: images for API 24–29 are
free, an accessibility service can be enabled on one with `adb`, and a good deal of the extra four
regimes could in fact be exercised without owning the phones. What an emulator does **not**
reproduce is most of what actually breaks this category — a vendor's power optimiser deciding the
service is idle, a skin's overlay restrictions, real touch latency, and the latched-touch freeze
itself. So the extra regimes would be *partly* covered and reported as covered, which is worse than
not claiming them. The distribution cliff at API 31 stands on its own regardless.

## Consequences

- `AccessibilityService.takeScreenshot()` (API 30) is available everywhere. A convenience, not the
  reason: a still frame for cropping a **Template** without a MediaProjection consent dialog.
- `GestureDescription.StrokeDescription` with `willContinue` (API 26) is comfortably below the
  floor, so continuous multi-segment swipes are always available.
- `targetSdk` is **36** regardless, so the newest rules are enforced on every device; `minSdk` only
  decides how far back fallbacks must be written.
- Lowering the floor later is additive work and stays possible. Raising it later takes support away
  from people who already have it, so starting high is the reversible direction.
